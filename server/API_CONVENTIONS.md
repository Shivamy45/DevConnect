# API Conventions

This document defines the backend conventions for DevConnect. Every new module and refactor must follow these rules.

---

# Core Principles

- Consistency over cleverness.
- Keep the architecture simple.
- Prefer readability over abstraction.
- Do not introduce new patterns unless there is a clear technical benefit.
- Preserve separation of concerns.

---

# Architecture

The project follows:

Routes → Controllers → Services → Database

Responsibilities:

- Routes map endpoints to controllers.
- Controllers handle HTTP concerns.
- Services contain business logic.
- Models interact with MongoDB.
- Business logic must never exist in routes.

Validation Responsibilities:

- Validation schemas validate and normalize request data.
- Controllers assume validated input.
- Services should not revalidate request format.
- Business validation (ownership, existence, permissions, etc.) belongs in services.

---

# Service Layer

Services are responsible for:

- Business logic.
- Database operations.
- Calling other services.
- Throwing `ApiError` when business rules fail.
- Returning only business data.
- Accept only validated input.
- Return plain business objects (DTOs), never HTTP response shapes.

Services must NOT:

- Access `req` or `res`.
- Send HTTP responses.
- Return HTTP status codes.
- Return `success` or `message` fields.
- Set cookies or headers.
- Know about Express.

Return only the data required by the controller.

Examples:

- Login → `{ user, accessToken, refreshToken }`
- Get User → `{ user }`
- Create Project → `{ project }`
- List Projects → `{ projects, pagination }`
- Delete → `null`

---

# Controller Layer

Controllers are responsible for:

- Reading request data.
- Calling services.
- Setting cookies when required.
- Returning HTTP responses.

Controllers must NOT:

- Contain business logic.
- Access the database directly.

Every exported controller function must end with the suffix `Controller`.

Example:

- `loginController`
- `registerController`
- `getCurrentUserController`
- `createProjectController`

---

# Response Format

Every successful response must follow:

```json
{
  "success": true,
  "message": "...",
  "data": {}
}
```

If no data is returned:

```json
{
  "success": true,
  "message": "...",
  "data": null
}
```

For collection endpoints:

```json
{
  "success": true,
  "message": "Projects fetched successfully.",
  "data": {
    "projects": [],
    "pagination": {}
  }
}
```

Use descriptive resource names (`users`, `projects`, `connections`, etc.) instead of generic names like `items`.

---

# HTTP Status Codes

- GET → 200
- POST (Create) → 201
- PUT/PATCH → 200
- DELETE → 200
- Login → 200
- Logout → 200

---

# Naming Conventions

## Services

Use only these verbs:

- get...
- list...
- create...
- update...
- delete...

Avoid mixing verbs such as `fetch`, `find`, or `retrieve` unless technically necessary.

## Controllers

Every exported controller function ends with `Controller`.

---

# Error Handling

Business failures must always throw `ApiError`.

Never return:

- false
- undefined
- error objects
- success flags
- null to indicate an error

Unexpected errors should bubble to the global error middleware.

---

# Code Quality

- Remove duplicate logic.
- Remove dead code.
- Remove unreachable code.
- Keep functions focused.
- Reuse existing utilities before creating new ones.
- Reuse existing services instead of duplicating business logic.
- Keep one source of truth for each business operation.
- Avoid unnecessary abstractions.
- Avoid premature optimization.
- Do not introduce helper utilities unless reused in multiple places.

---

# Search Conventions

- Use POST for complex search endpoints.
- Accept structured filter objects instead of parallel arrays or comma-separated query parameters.
- Perform pagination in the database whenever possible.
- Expose only public fields in search responses.
- Resolve public IDs to Mongo ObjectIds inside the service layer before querying.
- Keep search-specific business logic inside the corresponding service.

---

# AI Development Workflow

Before implementation:

1. Design the feature.
2. Finalize business rules.
3. Design the database changes.
4. Design the API contract.
5. Decide request and response shapes before implementation.
6. Define validation rules.
7. Review edge cases.
8. Decide whether the task should be implemented manually or generated by AI.

AI should primarily generate repetitive implementation such as:

- Models
- Controllers
- Services
- Routes
- Validation schemas
- CRUD logic
- Boilerplate tests

AI should not redesign APIs, introduce new abstractions, or change established architecture unless explicitly requested.

After generation, every change must be reviewed for:

- Architecture
- Security
- Validation
- Authorization
- Performance
- Query efficiency
- Error handling
- Naming consistency
- Duplicate logic
- Dead code

AI should never introduce new architecture, abstractions, utilities, or patterns unless explicitly requested.
